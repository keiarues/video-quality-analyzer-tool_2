# 全体評価と部分評価の処理時間調査

測定日：2026-11-15

測定前の本体：`365d0a5`。本体の評価コマンドを維持し、任意の時間計測通知を追加して測定した。

## 結論

- SSIM・PSNRでは、評価対象を約20%にしても総時間は約2～3%しか短くならなかった。最後の対象区間まで未評価フレームも復号していることが大きな負担になっている。
- VMAFは指標計算も重く、同じ均等配置で148.5秒から60.9秒へ約59%短縮した。部分評価の効果は指標により異なる。
- 実験用の入力シーク＋フレーム位置補正では、SSIMの均等配置を39.8秒から11.9秒へ約70%短縮し、1799フレームのSSIM値列が現行方式と一致した。
- SSIM・PSNRの同時計算は80.9秒から41.0秒へ約49%、VMAFの8スレッド指定は58.0秒から43.4秒へ約25%短縮した。どちらも今回比較した評価値は一致した。
- 高速化は通常アプリへ未適用。今回追加したのは任意の時間計測通知と診断・実験ツールで、通常アプリのFFmpegコマンドと評価対象の選択処理は変更していない。

## 1. 現行SSIMの全体・部分評価

元動画FFV1＋比較AV1。時間は3回の中央値。部分評価は比較対象との共通範囲に配置した。

| 方式 | 集計フレーム数 | 全体に対するフレーム数 | 経過秒・中央値 | 最小～最大秒 | 全体に対する短縮 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全体 | 8977 | 100% | 41.482 | 41.352～43.381 | ― |
| 時間範囲240～250秒 | 300 | 3.3% | 34.252 | 33.300～36.093 | 17.4% |
| 60秒ごとに先頭10秒 | 1499 | 16.7% | 34.421 | 33.429～34.604 | 17.0% |
| 10秒×6区間の均等配置 | 1799 | 20.0% | 40.252 | 40.137～41.687 | 3.0% |

時間範囲指定も入力側シークを使っていないため、240秒地点へ移動するまでの復号が必要になる。周期指定の最後の区間は250秒付近で終わる。一方、均等配置は最後の区間を末尾へ置くため、動画全体に近い範囲を復号する。

## 2. 他の指標とH.265での追加確認

均等配置は10秒×6区間。SSIM＋AV1だけは上表の3回中央値、他は各1回であり、有意差の判定には使用しない。

| 比較動画・指標 | 全体・秒 | 均等配置・秒 | 時間短縮 | 集計フレーム数・全体／部分 |
| --- | ---: | ---: | ---: | ---: |
| AV1・SSIM | 41.482 | 40.252 | 3.0% | 8977／1799 |
| AV1・PSNR | 40.888 | 39.915 | 2.4% | 8977／1799 |
| AV1・VMAF | 148.463 | 60.942 | 59.0% | 8977／1799 |
| H.265・SSIM | 34.173 | 34.924 | 短縮を確認できず | 8976／1798 |

VMAFは評価フレーム削減による効果が大きかった。SSIM・PSNRについて「部分評価を使えば処理時間も対象割合に比例して減る」とは言えない。

H.265は現行ログの集計件数がAV1より1件少なかった。表はサービスが返した実際の集計件数を記録した。この差の原因やフレーム同期精度は今回再判定しておらず、新しい入力シークを他コーデックへ展開する際の検証項目とする。

## 3. 時間がかかる処理の切り分け

元動画FFV1＋比較AV1で、FFmpegの処理を段階的に取り除いた診断。各1回。

| 診断用処理 | 経過秒 | FFmpeg CPU秒 |
| --- | ---: | ---: |
| 両動画を読み込み、圧縮データをそのまま破棄（復号なし） | 0.727 | 0.922 |
| 元動画FFV1のみ復号 | 29.957 | 403.688 |
| 比較動画AV1のみ復号 | 23.158 | 62.734 |
| 両動画を復号、品質計算なし | 38.248 | 495.219 |
| 両動画を復号＋均等配置の選択、品質計算なし | 49.719 | 467.141 |
| 両動画の先頭10秒だけ復号・選択、品質計算なし | 1.209 | 13.156 |

読み込みだけは短く、復号を入れると数十秒になる。キャッシュが温まった今回の条件では、圧縮データを読むことより、映像を復号する処理の負担が大きい。元動画のFFV1側も重いため、比較側AV1の改善だけでは残る負担がある。

ただし、単独復号・2入力復号・品質計算は処理の重なり方が異なるため、各経過時間を足して厳密な内訳にはできない。品質計算なしの2入力診断は2出力、本体は品質フィルターを通した1出力であり、スケジューリングも異なる。特に49.719秒を「selectフィルター単体に追加で約11秒かかった」とは解釈しない。

本体サービス内の時間計測では、SSIM全体の集計が中央値0.007秒、均等配置が0.009秒。VMAF全体でもログ解析・集計は0.060秒だった。取得済みメタデータで評価サービスを呼んだ範囲では、99.9%以上がFFmpegの起動・実行・待機にあり、C#側のログ解析高速化の優先度は低い。

## 4. 短縮できる箇所を実験した結果

### 4.1 評価区間ごとの入力シーク

現行方式は末尾近くまで復号してから対象外フレームを捨てる。実験では評価区間ごとにFFmpegを起動し、入力側の`-ss`で区間近傍へ移動した。

| 試作 | 経過秒 | フレーム数 | 現行値列との照合 |
| --- | ---: | ---: | --- |
| 時刻だけで直接シーク | 11.564（2回中央値） | 1800 | 不一致判定460件。件数差も含む |
| シーク＋元時刻によるフレーム選択補正 | 11.876（2回中央値、11.831～11.920） | 1799 | 全1799件でSSIM値が一致、最大差0 |
| 補正付き試作の比較用現行方式 | 39.838（1回） | 1799 | 基準 |

補正付き試作では、対象開始の1秒前を入力シーク位置とし、`-copyts`で元の時刻を維持する。各ストリームの開始時刻を差し引き、`round((t-start)*fps)`でCFR元番号を求め、要求した番号範囲だけを選ぶ。入力の長さも区間付近までに制限し、選択後に時刻を連続化して評価する。

この試作は現行方式に対して約70.2%短縮した。単に`-ss`を入れるだけでは、端数時刻や各入力の時刻精度の違いにより同じフレームを評価できなかったことにも注意する。

確認したのはこのFFV1＋AV1のSSIM値列で、全画素ハッシュを独立照合したものではない。他コーデック・異なる開始時刻・様々なシーク位置の確認は導入前に必要。VMAFを区間ごとに分ける場合は、時間方向の特徴量と区間境界の扱いも別途決める必要がある。

FFmpegの入力側`-ss`は通常、前方のシーク可能位置から必要分を復号する。[FFmpeg公式の入力シーク説明](https://ffmpeg.org/ffmpeg.html#Main-options)

### 4.2 複数指標で復号を共有する

現行は指標ごとにFFmpegを起動し直す。SSIMとPSNRの2指標を1つのFFmpeg内で`split`して計算した。均等配置・各1799フレーム、各1回。

| 方式 | 経過秒 |
| --- | ---: |
| SSIMを単独実行 | 40.271 |
| PSNRを単独実行 | 40.677 |
| 単独実行の合計 | 80.948 |
| 復号を共有した同時計算 | 41.004 |

約49.3%短縮。SSIM・PSNRともに全フレームの値が単独実行と一致し、最大差は0だった。複数指標を使う場合に有望で、1指標だけを選ぶ場合の短縮にはならない。VMAFを含む同時計算や、指標の非対応・失敗時に他指標の結果を保持する動作は未検証。

`split`はフレーム列を複数のフィルターへ分配する。[FFmpeg公式のsplit説明](https://ffmpeg.org/ffmpeg-filters.html#split_002c-asplit)

### 4.3 VMAFの計算スレッド数を明示する

現行のlibvmafは`n_threads`を指定せず、フィルターの既定値0を使用する。8スレッドを明示する実験を行った。均等配置・1799フレーム、各1回。

| 設定 | 経過秒 | FFmpeg CPU秒 |
| --- | ---: | ---: |
| 既定 | 58.007 | 509.281 |
| `n_threads=8` | 43.394 | 562.266 |

約25.2%短縮し、全1799件のVMAF値が一致、最大差0だった。ただしCPU秒は増えている。8がすべてのPCや他処理との同時実行で最適とは確認していない。モデルと評価フレームを維持して短縮できる候補として扱う。

## 推奨する次の作業

1. **部分評価の区間単位入力シークを専用画面で検証する。** 単一指標のSSIMでも効果が大きい。元フレームの画素照合、全テストコーデック、開始時刻、境界、中止、結果再利用、進捗の時刻変換を確認してから本体へ組み込む。
2. **複数指標の同時計算を検討する。** SSIM＋PSNRで効果と値の一致を確認済み。VMAF・非対応指標・途中失敗時の仕様を先に整理する。
3. **VMAFのスレッド設定を検討する。** このPCでは短縮できたが、CPU負荷との兼ね合いも含めて設定方法を決める。
4. 複数比較動画の評価時に元動画の復号・選択フレームを共有する案もあるが、時間短縮率とメモリ量は今回未測定。C#側のログ集計やCSVの最適化は優先度が低い。

## 再現手順・保存データ

主なSSIMの3回測定で成功した実行は次のとおり。元動画と比較動画のパスはそれぞれ1つの引数として渡す。

```powershell
$reference = (Get-ChildItem test-data -File -Filter '*reference.mkv').FullName
$candidate = (Get-ChildItem test-data -File -Filter '*qvbr 32*').FullName
& ./tools/dotnet/dotnet.exe ./tests/VideoQualityAnalyzer.Smoke/bin/Release/net10.0/VideoQualityAnalyzer.Smoke.dll $PWD --quality-timing $reference $candidate --phase core --metric Ssim --repeats 3
```

測定ツールは、あらかじめ `tools/dotnet/dotnet.exe build tests/VideoQualityAnalyzer.Smoke -c Release --no-restore -m:1 /nodeReuse:false` でビルドした。以降の切り分け・試作では次のコマンドが成功した。


- 個々の測定結果は `measurement-results/quality-timing/<日時と条件>/results.json`、集計は同フォルダーの `summary.csv` に保存する。
- 今回の結果の保存版は[部分評価処理時間データ/2026-11-15](部分評価処理時間データ/2026-11-15/README.md)を参照。動画のフルパス・音声データ・原動画は含めない。
