# C#・WPF版 移行検証仕様書

更新日: 2026-10-28  
対象: 新規検証プロジェクト。現行Python版の変更指示ではない。  
参照: [現行仕様書](仕様書.md)、[現行詳細設計書](詳細設計書.md)

## 1. 目的と結論の出し方

現行Python版で遅いと感じられる「2画面プレビューの30/60 fps再生」と「表示動画の切り替え」を、同じWindows PC・同じ動画でC#・WPF版と比較する。**C#への書き換えだけで改善するとは判断しない。** 現行は再生時刻を約40 msごとに更新するため表示要求の上限が約25回/秒であり、OpenCVから受け取った画像をBGR→RGB変換、拡縮、Pillow画像化、Tk画像化して表示している。動画切り替えでは新しい`VideoCapture`を開き、左右の結果がそろうのを待つ。これらの経路を変えた結果として改善するかを計測する。

検証結果は、ハードウェア、動画条件、実測値、失敗した動画、採用した再生方式を含む報告書にする。目標に届かない場合も、どの段階（読み取り、デコード、同期、描画、ファイル切り替え）が支配的だったか記録する。

## 2. 検証範囲

### 2.1 最初に作る検証アプリ

- Windows 11、x64、.NET 10、C#、WPFの独立した新規プロジェクトとする。日本語UIを使う。現行Pythonコード、設定ファイル、成果物は変更しない。
- 動画一覧へ複数ファイルを追加できる。元動画1本と比較動画を選び、左・右の最大2画面を再生する。同じ時刻を基準として再生、一時停止、停止、シーク、1コマ送り、表示対象の切り替えを行う。
- 左画面の音声のみ出す。音量、ミュートを用意する。音声のない動画でも映像を継続する。
- 選択規則は現行に合わせる。選択なしは原則「元動画＋先頭または直前の右動画」、比較動画1本選択は「元動画＋その動画」、2本以上選択は一覧順の先頭2本。対象を変えた際は変わらない側の画を維持する。
- 画面に現在時刻、左右の動画名、動画情報、実測の性能情報を表示する。コーデック・解像度・公称/平均fps・長さはFFprobeから取得する。
- 左右の動画領域は、それぞれ60.00 fps素材を等倍で全フレーム表示できることを目標とする。動画デコード・提示の経路を、時刻表示、シークバー、一覧、性能表示など動画以外のUI更新周期から分離する。動画以外のUIに60回/秒の更新は要求しない。
- 品質評価、グラフ、CSV、グループ管理は初期検証アプリの範囲外とする。移行判断後の完成版要件を第6章に定める。

### 2.2 比較する2段階の実装

| 段階 | 内容 | 判断 |
| --- | --- | --- |
| A: 短期試作 | WPFの`MediaElement`を左右に配置し、共通の再生制御器から操作する。音声は左だけ有効。 | 手早く、通常の2画面再生と切り替えの改善余地を確認する。フレーム単位の厳密同期やデコード方式の制御は保証しない。 |
| B: 必要な場合 | `Media Foundation Source Reader`で各動画を読み、サンプルの時刻で左右をそろえ、GPU上の映像をWPFへ渡す専用プレビューへ置き換える。 | Aがフレーム精度・fps・切り替え目標に届かない場合、または対象コーデックを開けない場合に着手する。 |

段階Aの`MediaElement`でfpsが改善しても、左右同期とコマ送りの精度が不足する場合は段階Bが必要となる。段階Aで60 fpsの提示を実測できない場合も、達成と判定せず段階Bへ進む。段階BでもOS・GPU・コーデック・解像度次第で60 fpsは保証できないため、満たせる条件と満たせない条件を報告する。どちらの段階でも、未対応コーデックを表示できたと偽らず、エラーと再生方式を示す。

## 3. 性能目標と測定方法

目標値は**検証用の暫定受け入れ基準**であり、現行アプリの実測値ではない。測定したfpsはタイマー呼び出し回数やデコード要求数ではなく、実際に画面へ提示された**異なるソースフレーム数**を基準にする。デコード済みや描画キュー投入済みのフレームを提示済みとして数えない。段階Aで提示フレームを正確に数えられない場合はOSの描画トレース等による外部計測を行い、「正確な提示fpsは未測定」と明記する。段階Bでは提示時刻とフレームIDを直接記録し、可能な範囲で画面上の実提示と照合する。

| 指標 | 暫定目標 | 測定の定義 |
| --- | --- | --- |
| 30 fps素材の2画面再生 | 準備期間を除く各1秒窓の95%以上で、左右それぞれ実効29 fps以上 | 1秒窓で異なる提示フレームを数える。冒頭2秒は準備期間として除外 |
| 60.00 fps素材の2画面再生 | 準備期間を除く連続30秒で、左右それぞれ期待される1800フレームを順序どおり提示し、欠落0とする。動画領域の目標は実効60.00 fps | ソースPTSと提示フレームIDから、同じフレームの重複を除いて数える。ディスプレイの実測更新率は60.00 Hz以上とし、提示間隔・欠落数も記録 |
| 左右の時間差 | 通常再生で95パーセンタイル33 ms以下 | 表示した左右フレームのPTS差を記録。段階AでPTSが取れなければ判定保留 |
| 動画切り替え | 同一時刻の新しい右画面が見えるまで中央値300 ms以下、95パーセンタイル800 ms以下 | 一覧選択操作から新しい動画の最初の表示まで。操作時点と初回提示時点を記録 |
| シーク | 両画面が指定時刻付近に揃うまで95パーセンタイル500 ms以下 | 10か所を順不同で操作。実フレームPTSを記録 |
| 操作応答 | 操作からボタン・選択表示の変化まで95パーセンタイル100 ms以下 | UIスレッドの応答時間を別に記録 |

60.00 fpsの判定は、PTSが60.00 fps相当のCFR素材を用い、左右とも動画領域が見える状態で、30秒の計測区間に属する1800フレームを対象とする。区間の始点・終点はソースPTSで固定し、境界の端数を欠落として扱わない。59.94 fps素材はその公称レートに応じた期待フレーム数で別に判定し、60.00 fpsと混同しない。30/60 fpsは、動画自体がそのフレームレートであり、表示装置も必要な更新率を持つ場合だけ判定する。VFR素材はfps達成率よりPTSに基づく遅延・同期を優先する。画面が非表示・最小化中の計測結果は採用しない。低速ストレージ、長いGOP、ソフトウェアデコード時の結果は条件を分けて報告する。60 fps未達時は欠落がデコード、同期、提示、表示装置のどこで生じたか切り分ける。

### 3.1 比較手順

1. 同一PCで現行Python版と新アプリをRelease構成で実行する。電源設定、GPU、ディスプレイHz、ウィンドウサイズ、拡大率、音量、他の高負荷処理を固定する。
2. 同じローカル動画を使う。最低限、1080pのH.264 30/60 fps、4KのH.264またはHEVC 30/60 fps、VFR、長いGOP、音声なし、再生できない形式を含める。元動画と比較動画の組み合わせ・表示サイズを記録する。
3. 各組み合わせで初回（冷状態）と2回目以降（温状態）を分け、冒頭2秒の準備期間を除いた連続30秒再生を3回、動画切り替えを10回、ランダムシークを10回実行する。中央値、95パーセンタイル、最悪値、左右差、CPU/GPU/メモリを記録する。
4. 現行版には測定用の計測点を別の作業コピーで追加してよい。元リポジトリの既存コードや結果をベンチマークのために書き換えない。現行版の表示fpsを正確に取れない場合は、その制約を報告書に記す。
5. 段階Aの結果で「全対象動画を開け、fps・切り替え・同期・コマ送りの目標を満たす」なら段階Bを省略できる。いずれかが未達または測定不能なら段階Bで原因を切り分ける。

## 4. 機能要件と例外

| ID | 要件 |
| --- | --- |
| P-01 | ファイル追加は複数選択とドラッグ＆ドロップに対応し、同じフルパスを重複登録しない。動画情報取得中も画面を止めない。 |
| P-02 | 2画面の再生基準時刻は1つとする。短い方の終端で止める。左右の音声が重ならないよう右側を常に消音する。 |
| P-03 | 切り替え中に古い右画面を「新動画」として表示しない。準備中の表示を重ね、同じ動画の左画面は途切れさせない。 |
| P-04 | 連続したシーク・選択変更では最新の要求だけを採用する。古い読み込み完了が新しい選択を上書きしない。 |
| P-05 | 1コマ送りは左画面の実PTSを使う。取得できない場合は平均fpsで近似したことを表示する。段階Aで正確なコマ送りができなければ未達として記録する。 |
| P-06 | ハードウェアデコードの実際の利用状況、フォールバック、コーデック非対応、デコード失敗を診断ログへ記録する。段階Aでは取得不能な情報を「不明」と表示する。 |
| P-07 | ファイル消失・破損・音声なし・映像なし・デバイス喪失時に落ちず、対象スロットに日本語の状態を示す。再生できる片側は続行する。 |
| P-08 | 表示対象から外したファイルの読み取りハンドルを解放する。事前読み込みは上限付きで、ファイルロックが続く時間を測る。 |
| P-09 | 診断ログには原則として動画のフルパス、音声データ、外部コマンド全文を残さない。性能ログには匿名化した動画IDと条件を使う。 |
| P-10 | 動画の提示は動画以外のUI更新を待たせない。時刻、シークバー、性能値などの定期表示は必要な頻度（目安4～10回/秒）でまとめて更新し、動画フレームごとにWPF UI全体を再描画しない。操作への応答は別途100 ms目標を維持する。 |

## 5. 移行可否の判定

- **移行を進める**: 段階AまたはBが対象動画で目標を満たし、現行版より実効fps・切り替え時間の少なくとも一方が明確に改善し、他方が悪化しない。左右同期・操作精度も満たす。
- **構成を再検討**: 目標未達だが、CPU画像変換、GPU→CPUコピー、ストレージ待ち等の支配要因が分かり、別の表示経路で解消見込みがある。
- **移行を見送る**: 対象PCと動画で両段階とも改善せず、問題がデコーダー能力、GPU、ストレージ、表示装置等に支配される。

判定報告書には測定できなかった項目と理由を必ず載せる。単なる「C#版の方が速い」という主観評価で決めない。

## 6. 移行決定後の完成版仕様

検証に合格してから、[現行仕様書](仕様書.md)の機能を順番に再実装する。初期検証アプリを完成版と呼ばない。完成版では以下を維持する。

- 元動画1本と複数の比較動画の登録、元動画変更時の評価結果破棄、グループ、一括選択、一覧ソート、ファイル消失時の確認。
- VMAF・SSIM・PSNRの全フレーム評価、進捗・途中結果、中断、完了済み組み合わせの再利用、FFmpeg/FFprobeの検出と`libvmaf`確認。品質計算のFFmpegコマンドと集計規則は現行に合わせる。
- 指標別のフレーム推移、平均品質対ビットレート、グループ線、グラフクリックでシーク、可変fpsの時刻、CSV 2種とUTF-8 BOM。
- 再生・一時停止・停止、前後1秒/5秒、コマ送り、ズームと左右同期スクロール、音量・ミュート、設定、ログ、ポータブル配布。
- 現行で未実装のワイプ比較、差分ヒートマップ、点滅比較、自動エンコードや自動補正、プロジェクト保存は移行に混ぜない。

品質指標の評価は引き続きFFmpegの外部プロセスが実行するため、C#化による評価計算そのものの高速化は要件にしない。旧`settings.json`の読み取りは安全な既知キーだけを取り込み、旧版の設定ファイルを書き換えない。動画一覧・評価結果は現行同様、起動間で復元しない。

## 7. 技術上の根拠

- 現行の約40 ms更新、OpenCV/Pillow/Tk変換、左右結果待ち、対象変更でcapture再オープン: `src/video_quality_analyzer/playback_ui.py`、`preview.py`、`preview_decoder.py`。
- WPFの`MediaElement`は再生・停止・位置変更を提供するが、精密な2系統同期や提示フレームの計測を自動では行わない: [MicrosoftのWPFメディア解説](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/multimedia-overview)。
- `Media Foundation Source Reader`は読み取り・デコードを担う一方、描画時計や音声同期はアプリ側が用意する: [MicrosoftのSource Reader資料](https://learn.microsoft.com/en-us/windows/win32/medfound/source-reader)。シーク先は通常キーフレーム付近であり、指定フレームへはPTSを見ながら読み進める: [シークの説明](https://learn.microsoft.com/en-us/windows/win32/medfound/processing-media-data-with-the-source-reader)。
- WPFの`D3DImage`はDirect3D 9との連携に対応するが、サーフェスのコピーや同期に費用がかかり、複数枚で悪化し得る: [Microsoftの性能上の注意](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/performance-considerations-for-direct3d9-and-wpf-interoperability)。
- .NET 10のサポートとWindows対応: [Microsoftの.NET対応表](https://learn.microsoft.com/en-us/dotnet/core/install/windows)。
